Upon seeing the images, the task was apparent. It was a matter of aligning the individually-exposed-RGB photographs together to create a single colored image, but the steps to do so was anything but simple. To determine a "good alignment," we used both euclidean distance and normalized cross-correlation as possible scoring functions for the images' alignments. With euclidean distance, when two images match, the individual pixels' intensities would be assumed to be closest to each other, so when subtracted, they should produce the least error. Squaring and summing it all up ensures that dynamic is applicable to all the pixels as well, meaning all pixels in the images aligns with their closest. Normalized cross-correlation takes it a step further, accounting for overall differences in photo quality due to lighting difference by normalizing each pixel before measuring their similarity with their aligned counterpart. The closest the resulting value is to 1 or -1 means it is the closest to a match or inverse match. To keep things simple, I turned NCC's value negative, so I could treat it like Euclidean distance's score, in that I needed to find the minimum to find the best corresponding offset.

First, I cropped the borders of all images by a preset fraction to remove any possible interference to the scoring calculation. Then I started the naive implementation of the offset finder that did not account for image resolution. Given a preset max offset, for me 15, I rolled the red image for all possible x and y offset combination within [-15, 15] and compared it to the blue image one by one using one of the scoring functions. I did the same with the green image. It worked for all the smaller images.

The Algorithm:

The biggest issue with the naive offset finder implementation is that it cannot properly handle big data types like the .tif. With resolutions of that sizes, a bigger range of offsets would need to be searched through and that would just take more time.

The solution to this is to use image pyramids. By using lower resolution versions of the image, using the small search range that you would use for the naive offset finder implementation would actually cover a more significant amount of ground than with the bigger resolutions. Once you find the offsets that best fit for lower resolutions, you would go up a resolution and search the same range but now at the scaled up offsets you found from the previous layer. It essentially like repeatedly searching for the start point for better finetuning in subsequent searches.

To create the image pyramid, you would do Gaussian filtering on the image via convolving over with a Gaussian kernel then subsample, taking every other row. This would cut the resolution by a factor of 2 and then you would rinse and repeat until you reach a layer where you deem the resolution small enough to be a decent stopping point. After the image pyramid is created for the R, G, and B parts, I would go down the layers from the top and conducting naive offset finder search on the current layers and passing best fit offsets down to the next layer, scaling them up to be the starting point of the naive offset finder search again. Rinse and Repeat until I have reached the very bottom, in which the cummulative offsets I acquired is likely the right one for best fit alignment.

Despite this optimization, I was still having trouble with the long search times, so I implemented another optimization to make my naive offset finder run faster. Instead of going one rolled image at a time, I made the scoring section apply to multiple rolled images in one iteration instead. By putting my rolled images back to back, I can conduct matrix operations on them such that I would receive the scores of multiple rolled images at once instead of one at a time. This optimization significantly decreased the wait time per big image by a factor.
